# NavTasks — обязательный регламент разработки

## Начало каждого чата
- Репозиторий: sergbokarev95-arch/NavTasks. Использовать подключённый GitHub; проверять реальный доступ через его инструменты, а не по сетевому доступу локального контейнера.
- Канонический контекст: ветка `docs/navtasks-development` (только документация). Сначала читать AGENTS.md, docs/development/HANDOFF.md, CURRENT_STATE.md, NEXT_TASKS.md, DECISIONS.md **из этой ветки**. CHANGELOG_DEV.md — история, читать нужный раздел по запросу; архив не является актуальной инструкцией.
- Проверить фактические HEAD, build.gradle.kts, актуальные feature-ветки, последний релиз и Actions. Не считать main или ветку документации актуальными исходниками. При расхождении GitHub факты первичны; обновить краткий контекст. Не принимать pending за success.
- Если уже есть незавершённая сборка нужной версии, продолжить её проверку. Не начинать заново и не запускать дубль. Не изменять HEAD активной release-ветки до окончания проверки и публикации.

## Полный цикл (для согласованного изменения приложения)
1. Проверить актуальный исходник и создать резервную ветку; уточнять только действительно несогласованные изменения.
2. Внести точечные правки, проверить diff, совместимость хранения и регрессионные тесты.
3. Проверить versionCode/versionName, оригинальный signer, workflow и recovery с большим versionCode. Создать коммит и отправить в правильную feature-ветку.
4. Проверить, что запущен ровно нужный GitHub Actions run для нужного SHA. Запуск push-workflow не дублировать dispatch.
5. В этом же запросе проверять jobs/steps/status по мере выполнения, показывать пользователю реальные этапы. При failure получить журнал, определить причину, исправить только необходимое и повторно проверить; при активном run не считать отсутствие архива логов ошибкой сборки.
6. Успех: полный JVM test suite, APK release build, package/version/non-debuggable и оригинальный signer, публикация. Проверить релиз и фактический APK asset (browser_download_url, размер, digest); то же для совместимого recovery.
7. Завершить после получения проверенного APK и ссылки. Если технический предел сеанса не позволяет продолжить, честно указать конкретное ограничение, последний статус, run URL и какой этап ещё не подтверждён. Не выдавать фиктивную ссылку, не имитировать фоновую работу и не заставлять пользователя запрашивать статус, пока можно проверять в текущем запросе. Плановая автоматизация — только с явного согласия и не замена обычному циклу.
8. Обновить канонические документы: текущий статус и точку продолжения переписывать, решения менять только при изменении согласованного решения, историю добавлять только в CHANGELOG_DEV. Не копировать одинаковый исторический абзац во все файлы. Документирование не должно перезапускать сборку.
9. Выдавать пользователю кратко: что изменено, проверенные тесты/CI, ссылки Beta и Recovery, известные ограничения, что проверять на устройстве. CI не означает проверку на HONOR/Samsung.

## Защитные границы
- Без явного согласия не публиковать stable OTA, не менять stable feed, ключ подписи, пакет, настройки профиля, не сливать beta в main.
- Сохранять профили, историю выполнений, чек-листы/вложения, переносы, правила повторения, настройки, уведомления, импорт/экспорт. Не исправлять несогласованные соседние модули.
- Если изменения только в документации, APK не требуется: проверить коммит и содержимое, не запускать Android CI без причины.
- Это правила проекта, а не гарантия изменения интерфейса ChatGPT, времени жизни чата или доступности инструментов.
